# FMO target contract

An FMO device is not one machine. It is a host plus a fleet of microVMs on an internal
network, and almost every mistake in this workflow comes from talking to the wrong one or
calling it by the wrong name. This skill is the shared map; the other `fmo-*` skills
assume it.

## Where the device details come from

`.claude/config.yaml` is the source of truth, keyed by machine: `alienware-m18-r2`,
`dell-7230`, `dell-7330`, `lenovo-x1-gen11`, `lenovo-x1-gen12`, `demo-tower-mk1`,
`tower-5080`. Read it rather than asking the user for things it already knows:

```bash
.claude/scripts/fmo-config.py --list
.claude/scripts/fmo-config.py --device dell-7330                 # every field
.claude/scripts/fmo-config.py --device dell-7330 --field host_ip # one field
```

Fields that matter here: `host_ip` (the device's reachable address), `usb_iface` (the
host-side NIC facing it, typically `ghaf-usb`), `serial_device` / `serial_baud`,
`install_disk`, `flash_drive`, `fmo_target`, `installer_target`, `netboot_target`,
`netboot_iface` / `netboot_mac`.

Per-machine values — `host_ip`, `ssh_identity`, `install_disk`, `flash_drive`,
`serial_device`, `netboot_iface`, `netboot_mac` — live in the gitignored
`.claude/config.local.yaml`, merged over the shared file per field. `config.yaml`
deliberately leaves them null, because they describe a particular desk rather than the
project. `config.local.yaml.example` shows the shape. Always go through `fmo-config.py`:
it implements the merge, and reading either file directly gets you the wrong answer.

If `host_ip` is null in both, ask the user for the address once and offer to write it into
**`config.local.yaml`** — guessing an address on a lab network can land you on someone
else's device, and writing it to the tracked file leaks lab topology into the repo.

Note `ssh_identity`: when a device is reached by a key ssh would not offer by default, every
command fails with "Permission denied (publickey)", which reads like the device being down
rather than a missing key.

## The address map

Verified by evaluating `nixosConfigurations.fmo-dell-7330-debug.config.networking.hosts`.
The internal network is `192.168.100.0/24` and every VM resolves by name from any VM on it:

| Name | Address | Notes |
|---|---|---|
| net-vm | 192.168.100.1 | owns the physical NIC — this is what you reach from outside |
| ghaf-host | 192.168.100.2 | the hypervisor host; where `microvm@*.service` units live |
| audio-vm | 192.168.100.3 | |
| gui-vm | 192.168.100.4 | desktop, greetd, login |
| admin-vm | 192.168.100.5 | givc admin. The journal collector is **off** here, see `fmo-logs` |
| docker-vm | 192.168.100.101 | the FMO payload: Docker, DCI, onboarding. App-VMs start at .101 |

Generated by `ghaf:modules/common/networking/hosts.nix`, which numbers net-vm first, then
ghaf-host, then the remaining system VMs, then app-VMs from .101 — that ordering is
structural rather than configured. FMO enables exactly one app-VM (`fmo.appvms.docker`), so
unlike upstream there is only one .10x row. To confirm for a specific image, evaluate
`.config.networking.hosts` as above, or run `fmo-logs`' collector, which enumerates whatever
is actually there.

`docker-vm` is the main thing this repo adds over Ghaf, and it is where the FMO-specific
failures live. See `.claude/skills/fmo-logs/references/vm-map.md` for what each VM owns.

## Reaching things

The device's external address belongs to **net-vm**, because it holds the passed-through
NIC. Everything else is one hop further in:

```bash
ssh ghaf@<host_ip>                                            # lands on the device (net-vm side)
ssh ghaf@<host_ip> -- ssh ghaf-host                           # the hypervisor host
ssh ghaf@<host_ip> -- ssh gui-vm journalctl -b --no-pager     # a specific VM
ssh ghaf@<host_ip> -- ssh docker-vm sudo docker ps            # the FMO payload
```

For `nixos-rebuild` the same topology is expressed as ssh config by `ghaf-build-helper`,
which this repo pulls from the ghaf input and surfaces as `fmo-rebuild` in `nix/devshell.nix`
(the package definition itself is upstream, at `ghaf:packages/pkgs-by-name/ghaf-build-helper/`):

```
host ghaf-netvm   user root   hostname <target-ip>
host ghaf-host    user root   hostname 192.168.100.2   proxyjump ghaf-netvm
```

Which hop you need depends on the question. Host-level things — microvm units, PCI
passthrough, disko and LUKS, the hypervisor journal — live on `ghaf-host`. Anything about
the desktop, login or an application lives in its VM; anything about containers,
onboarding or DCI lives in `docker-vm`.

## One machine, one target

There is no generic laptop image here. Unlike upstream Ghaf, which folds its x86 laptops
into a single `intel-laptop-debug`, every FMO machine has its own target:

| Machine | Target | Installer | Netboot |
|---|---|---|---|
| alienware-m18-r2 | `fmo-alienware-m18-r2-debug` | `…-debug-installer` | `…-debug-netboot-installer` |
| dell-7230 | `fmo-dell-7230-debug` | | |
| dell-7330 | `fmo-dell-7330-debug` | | |
| lenovo-x1-gen11 | `fmo-lenovo-x1-gen11-debug` | | |
| lenovo-x1-gen12 | `fmo-lenovo-x1-gen12-debug` | | |
| demo-tower-mk1 | `fmo-demo-tower-mk1-debug` | | |
| tower-5080 | `fmo-tower-5080-debug` | | |

The naming is mechanical: `fmo-<machine>-debug`, plus `-installer` or `-netboot-installer`.
Only the `debug` variant exists today; `release` is commented out in
`targets/flake-module.nix`. Get the exact string from the config rather than assembling it:

```bash
.claude/scripts/fmo-config.py --device dell-7330 --field fmo_target
```

The trap here is not a name that fails — it is a name that *works*. Building a neighbouring
machine's target produces an image that boots, and then over-allocates VM memory or passes
through the wrong devices, because `modules/hardware/resources/<machine>.nix` is sized
against that machine's actual RAM and `modules/hardware/flake-module.nix` layers per-machine
USB and PCI overrides on top. `dell-7230` has under 8 GiB in total, so it is the one where
this shows up first, as an OOM that looks like a regression in whatever was running.

## Upstream modules are in the store, not in this tree

`ghaf` is a flake input. `/etc/hosts` generation, the desktop, greetd, givc, partitioning
and the system-VM bases are all upstream, so grepping this repo for them finds nothing and
the absence reads as "that does not exist" rather than "that is not here".

```bash
nix flake metadata --json | jq -r '.locks.nodes.ghaf.locked.rev'
```

Read the checkout at that revision, or read the deployed closure (below). When citing an
upstream file, write it as `ghaf:modules/...` so the next reader does not search this tree.

## Identifying what is actually running

Before trusting any conclusion about a device, confirm what is on it. A surprising amount
of debugging time goes to reasoning about code that was never deployed:

```bash
ssh ghaf@<host_ip> -- ssh ghaf-host  readlink /run/current-system
ssh ghaf@<host_ip> -- ssh gui-vm     readlink /run/current-system
ssh ghaf@<host_ip> -- ssh docker-vm  readlink /run/current-system
```

If that store path exists in your local store, you can read the *exact* configuration that
is running — `/nix/store/<hash>-nixos-system-gui-vm-*/etc/` holds the generated `pam.d/`,
`systemd/`, `hosts` and so on. Reading the real artifact beats re-deriving what you think
the Nix evaluated to, and here it beats it twice over: most of those modules are upstream,
so the rendered `etc/` is the only copy in reach without checking out the input.
